Instructions for agents

Everything on this site is a set of habits a careful engineer picks up over time. A coding agent has none of them, but it follows written rules well. This page is the AGENTS.md we recommend, so an agent can make schema changes on its own and tell you clearly what it did and what it left for you to decide.

Two files: AGENTS.md, the instructions, and check-database, a script the instructions tell the agent to run before it finishes.

Why agents need it written down

Asked to "add a currency to invoices", an agent with no instructions does what most of the internet does: writes 0042_add_currency.sql with an alter table, maybe edits the table's file too, and calls it done. Every habit on this site is invisible from the code alone:

  • that the table's file must never contain an alter, and is changed by a rework;
  • that @tag files look like ordinary SQL and must never be touched;
  • that adding an argument with create or replace function makes a second function and breaks every caller;
  • that a sqitch.plan conflict is resolved by regenerating, not by keeping both sides;
  • that some decisions, like a table rewrite or dropping a column, are not the agent's to make.

The file writes those down, in the order an agent needs them: where things are, which workflow fits the task, the rules, how to check, when to stop, and what to report.

Install it

  1. Add the instructions. Save AGENTS.md at the root of your repository. Codex and most other agents read AGENTS.md on their own. If you already have one, paste it in as a section. For Claude Code, add a line to CLAUDE.md that imports it: 
    @AGENTS.md
  2. Add the check. Save check-database as scripts/check-database and make it executable. Run it yourself once to see it pass.
  3. Fill in the details. Replace the guide URL placeholder, and change master if your main branch has another name. If your services are not written in Haskell, delete the hasql-check line.
  4. Give the agent the tools. sqitch, sqiff, sqint, create-migration, psql and a PostgreSQL it may create scratch databases on, with PG* variables pointing at it. With Nix: 
    nix shell nixpkgs#sqitchPg nixpkgs#postgresql_18 \
  github:kronor-io/sqiff github:kronor-io/sqint github:kronor-io/sqitch-with-templates

What the file says

SectionWhat it gives the agent
Where things areThe layout, and the instruction to read an object's definition instead of reconstructing it from migrations.
Choose the workflowA table from task to command: create an object, change a table, change a function or view, the multi-release recipes. Commands are given with every flag, because create-migration prompts when one is missing and sqitch opens an editor without -n.
RulesThe nevers and alwayses from the layout, functions and shipping safely, stated without exceptions.
Merging and rebasingThe regenerate-don't-merge procedure from git and review, and why a stale snapshot matters.
Check before you finishOne command, and what to do with sqint's findings: fix BLOCKs, never write a lint:ignore itself.
Stop and askThe judgement calls: rewrites, data loss, renames, backfills of unknown size, conflicts in lines already on the main branch.
ReportWhat changed, every hazard and what was done about it, which release each part belongs to, and every check with its result.

Two choices are deliberate. The agent may not suppress a lint finding: a lint:ignore records a human's decision, and an agent writing one defeats the point. And it reports the hazards it accepted instead of silently accepting them, so the reviewer reads them first.

The check script

An agent is only as careful as the check it runs at the end. scripts/check-database puts the important checks behind one command, so the instructions can say "run this" rather than describe a procedure:

$ scripts/check-database
== sqint: deploy scripts changed since master
== the plan only grows
== snapshots are not edited
== fresh database: deploy the whole plan
Deploying changes to db:pg:check_database_scratch
  + base_schemas ................................................. ok
  …
  + migrations/2026/11/2026-11-25-105014-add-column-billing.invoice.note .. ok
== revert this branch's 2 changes and deploy them again
  - migrations/2026/11/2026-11-25-105014-add-column-billing.invoice.note .. ok
  + migrations/2026/11/2026-11-25-105014-add-column-billing.invoice.note .. ok
== database checks passed

It reverts the branch's changes by counting them back from the end of the plan (sqitch rebase --onto @HEAD^2), not by name, because a reworked change's name is ambiguous. It deliberately does not use sqint's dynamic pass, which has known limits with reworks. Run it in CI too, so the agent's check and the merge check are the same.

Guardrails outside the file

Instructions are followed most of the time. For the things that must never happen, do not rely on them alone.

  • No production credentials. The agent's environment should reach a local or scratch PostgreSQL and nothing else. Keep production targets out of sqitch.conf; let your deploy pipeline hold them.
  • The pre-commit hooks from shipping safely catch edited snapshots and rewritten plan lines whoever makes them.
  • Review stays human. The agent's report is written for the reviewer: hazards first, then the checks. A pull request that changes the schema still needs a person to accept its costs.

We tried it

We gave Codex the example project from this site with the file at its root, and one task, phrased the way a product owner would:

"Invoices can now be in different currencies. Add a currency to billing.invoice: a three-letter ISO code, required. Every existing invoice is in SEK. Then billing.outstanding_for should report what a customer owes in one currency, SEK unless the caller says otherwise. Make the database change on a new branch and commit it."

It is a hard task on purpose: a required column on a table with rows, and a new argument on a function that already has two. Codex was not told about any of the tools. What it did:

  • Read the definitions, not the migrations, and chose create-migration non-nullable-column for the column.
  • Set the default to 'SEK' in the first step, so new inserts set the column before the not valid check starts rejecting them.
  • Added the format check not valid and validated it in its own change.
  • Reworked the table and the function after the migrations, with one shared tag.
  • Dropped the old (text, date) signature in the definition, gave the new argument a default, and added a drop of the new signature to the revert script.
  • Ran scripts/check-database, left sqint's warning for a human instead of suppressing it, and ended with the report in the four parts the file asks for.

We checked the result independently: the check passes, including reverting and redeploying all nine of its changes; the two existing invoices are SEK; and the function returns 120.50 in SEK and 0 in EUR for the same customer.

The trial also taught us three things, and the file now says them:

  • sqiff and the batched recipes. After the recipe, Codex ran sqiff table, which replays the branch's earlier changes in one transaction and stopped at the backfill's COMMIT with invalid transaction termination. Codex fell back to sqitch rework on its own, which was right. We fixed sqiff so its replay leaves the backfill's commits out (0.1.3.0), and the file says to use sqitch rework with older versions.
  • A parameter named like a column. It named the new argument currency, like the column, and had to refer to it as $3. In a SQL function the column wins, so the file now says to qualify or rename.
  • Backfills. The first version told agents to stop and ask before backfilling a table they could not size. Codex went ahead, and on reflection that is the right default for a batched backfill. The file now asks for every backfill to be listed in the report instead, with whether the table's size is known.
