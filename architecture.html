Designing the database

The tools make a schema change easy to write, review and ship. That matters most when the schema carries rules every service relies on. This is how Kronor designs a database to hold them.

Rules live in the database

A rule written in one service is a rule every other service can break. Put shared rules where every reader and writer has to pass through them, preferring, in this order:

  • Types and constraints for what a value may be: domains such as email_address or text_64, check constraints, foreign keys, exclusion constraints.
  • Generated columns and views for what can be computed from other data, so no service computes it differently.
  • Functions for operations that have to happen together, called as one statement in one transaction.
  • Statecharts for how an entity moves through its life.

Application code then reads and writes through a narrow, well-named surface, and a bug in one service cannot write a row that another service has to defend against. This is also why cheap schema changes matter: rules in the database have to be as easy to change as rules in code, or people stop putting them there.

Schemas by context

Split the database into schemas by what the data is about, not by technical layer. Each schema is created in the first change, base_schemas, with a comment saying what belongs in it.

create schema if not exists billing;
comment on schema billing is 'Invoices, payments against them, and their lifecycles.';

create schema if not exists customer_data;
comment on schema customer_data is
  'Personal data about customers. Protected by GDPR; other schemas refer to it by id only.';

create schema if not exists portal_api;
comment on schema portal_api is
  'Views and functions the merchant portal reads. Nothing else is exposed to it.';
  • Domain schemas such as billing hold tables and the functions that own them.
  • Personal data sits in its own schema, so its grants, retention and audits are in one place.
  • API schemas hold only views and functions. They are the contract a consumer such as a GraphQL layer reads, and you can change the tables underneath without changing it.
  • Transient data, such as a checkout in progress or a job queue, gets a schema of its own so it is never mistaken for a record.
  • Infrastructure keeps its own schemas: fsm for statecharts, and others for partitioning or scheduling.

The folder structure follows: database/deploy/billing/…, database/deploy/portal_api/…. sqiff takes --exclude-schema for infrastructure schemas you do not manage in the plan.

Lifecycles as statecharts

An invoice is drafted, sent, then paid or voided. The usual way to model that is a status column, and the usual result is that every writer has to know which moves are allowed, some of them get it wrong, and the history is overwritten with each update.

With statecharts, the lifecycle is a chart the database executes:

  draft ──send──▶ sent ──pay──▶ paid
    │              │
   void           void
    │              │
    └──▶ voided ◀──┘

database/statecharts/invoice_flow-1.0.scxml

<scxml xmlns="http://www.w3.org/2005/07/scxml"
       name="invoice_flow" version="1.0.0" initial="draft">
  <state id="draft">
    <transition event="invoice.send" target="sent"/>
    <transition event="invoice.void" target="voided"/>
  </state>
  <state id="sent">
    <transition event="invoice.pay"  target="paid"/>
    <transition event="invoice.void" target="voided"/>
  </state>
  <final id="paid">
    <onentry><script src="billing.on_invoice_paid"/></onentry>
  </final>
  <final id="voided"/>
</scxml>
  • One machine per row. The invoice table gets a state_machine_id bigint not null, indexed. A before insert trigger creates a machine with fsm.create_state_machine_with_latest_statechart, and an after insert trigger starts it.
  • Events instead of updates. Code sends select fsm.notify_state_machine(machine_id => …, event_name => 'invoice.pay'). The transition and its callbacks run in the statement that sends the event, inside the caller's transaction, so the new state commits with the rest of the data or not at all. To ask whether an event would move the machine before sending it, use fsm.is_valid_transition.
  • Callbacks write plain columns. billing.on_invoice_paid sets paid_at on the invoice, so ordinary queries read a column and never join the state log. create-migration function statechart writes the callback's skeleton.
  • Branch with events. The engine has no guards. When the next state depends on data, a callback looks at the data and sends the next event.
  • Queue slow work. A callback runs inside someone else's transaction. Calling a payment provider from it holds that transaction's locks for a network round trip; put a job on a queue instead.
  • A recorded history. fsm.state_machine_state keeps every state each machine entered, with timestamps.
  • Versioned charts. Each machine is created from a specific chart version. Changing the chart means a new version; rows created afterwards get it, and machines already running keep theirs.

The chart reaches the database as an ordinary sqitch change. On a development machine, the pg_statecharts_dev extension reads the SCXML and writes the change and its plan line; it reads files on the database server, so the repository has to be mounted into the postgres container at the same path:

mkdir -p database/{deploy,revert,verify}/statechart
psql -c "create extension if not exists pg_statecharts_dev cascade" \
     -c "select fsm.gen_statechart_sqitch_migrations(
           source_path           => '/repo/database/statecharts',
           sqitch_plan_file_path => '/repo/database/sqitch.plan')"

That adds statechart/invoice_flow-1.0.0. Its verify script checks that every callback exists and takes one fsm_event_payload, so the callback's change must come before the chart's in the plan.

When a status column is enough

Statecharts pay for themselves when a lifecycle has rules worth enforcing and a history worth keeping: payments, orders, onboarding. A flag that only ever goes from false to true does not need one. Start with the entity whose invalid transitions have already cost you an incident.

Roles per duty

Give each kind of work a group role with only the grants it needs, and give each service's login user one of them.

create role read_only_role nologin;
create role worker_role nologin;
create role portal_role nologin;

grant usage on schema portal_api to portal_role;
grant select on all tables in schema portal_api to portal_role;
alter default privileges in schema portal_api grant select on tables to portal_role;

grant portal_role to portal_service;   -- the login user

Roles and grants are files in the plan like everything else, and reworked when they change. sqiff keeps an object's grants when it drops and recreates it.

Say why, in the schema

Comment every schema, table and column with comment on. The comment travels with the object into psql, GraphQL descriptions and sqiff's describe output, where a comment in a source file never goes. Use SQL comments in the deploy file for the reasons behind a decision: why a table is insert-only, why a lock is taken up front.

Never break running code

The database deploys before the new application code, and the old code keeps running against the new schema until the rollout finishes. Every change has to work with both.

  • Expand, then contract. Add the new column, function or view in one release. Remove the old one in a later release, once nothing uses it.
  • Add parameters with defaults. A new function parameter without a default breaks every existing caller.
  • Keep composite types stable. Code that builds a value with row(…)::some_type breaks when the type gains a field.
  • Rename in two steps. create-migration rename-column-step-1 keeps both names in sync; step 2 ships after the code has moved.

hasql-check turns this into a test: before deploying, check the queries of the code that is currently running against the new schema. If any statement fails to prepare, the migration would break production. See CI and deploys.

Respect the locks

On a busy database, the danger in a migration is rarely the change itself but the lock it waits for, because every query queues behind a waiting ACCESS EXCLUSIVE request. The templates and linters agree on a small set of habits:
